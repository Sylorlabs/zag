# Zag GPU compiler and driver boundary

Zag owns the GPU language, semantic analysis, custom GPU IR, optimization,
scheduling, target code generation, proof-carrying kernel metadata, virtual
execution, runtime policy, synchronization, submission adapters, diagnostics,
and tuple-based certification.

Zag does **not** replace privileged operating-system or vendor GPU drivers,
firmware, PCIe enumeration, interrupts, display, power management, or device
reset. Those are the maintenance ceiling. A pure-Zag userspace adapter talks to
an installed stable driver interface.

| Zag target | Code generated by Zag | Existing driver boundary | Status |
| --- | --- | --- | --- |
| `amdgpu-gfx1010` | native RDNA1 ISA in ZGK1 | Linux AMDGPU DRM UAPI | compiler/strict VM plus bounded discovery, GPUVM, CPU-memory, and display-safe preflight; direct CS submission incomplete |
| `nouveau-native` | native NVIDIA ISA | Linux Nouveau DRM UAPI | planned, fail-closed |
| `intel-xe-native` | native Intel ISA | Linux Xe DRM UAPI | planned, fail-closed |

The compatibility tier is a separate, loader-backed portability path. It does
not promote the native DRM target or pretend that a shader API is a replacement
for the kernel UAPI:

| Compat target | Zag artifact | Host boundary | Local evidence |
| --- | --- | --- | --- |
| `vulkan-compat` | Vulkan 1.0 SPIR-V | `libvulkan.so.1` / RADV | bounded dispatch and 1024-element readback verified on RX 5700 XT |
| `opengl-compat` | GLSL 430 | EGL + Mesa OpenGL 4.6 | bounded dispatch and 1024-element readback verified on RX 5700 XT |
| `opencl-compat` | OpenCL SPIR-V plus pure-Zag OpenCL-C fallback | `libOpenCL.so` / ROCm ICD | bounded dispatch and 1024-element readback verified on RX 5700 XT |
| `cuda-compat` | PTX 6.5 | CUDA driver | artifact-only here; no NVIDIA GPU, fail-closed |
| `metal-compat` | MSL | Metal framework | artifact-only on Linux, fail-closed |

`tests/run_gpu_runtime.sh` generates the small C ABI harnesses in `/tmp` and
requires `ZAG_RUN_PHYSICAL_GPU=1` before submitting work. The gate applies an
external process timeout, uses tiny buffers, and checks every output element;
the default run compiles and validates without touching the display-bound GPU.
This compatibility evidence is intentionally separate from native
`amdgpu-gfx1010` certification.

The native AMDGPU boundary currently stops at a deliberate preflight. The
strict `tests/run_linux_drm.sh` gate queries the live render node, validates
GFX10/compute IP and GPUVM limits, maps one 4 KiB GTT BO, and performs one
4 KiB CPU readback. `linux_amdgpu_native_preflight` refuses a declared
display-bound card unless both `allow_shared_display_override` and
`acknowledge_reset_risk` are true. Even with those switches, the result marks
`native_submit_implemented=false` and returns `E_AMDGPU_SUBMIT_UNIMPLEMENTED`:
no `DRM_IOCTL_AMDGPU_CS`, fence wait, reset, or hardware certification is
claimed yet.

The three loader-backed adapters share a typed `ZagGpuCompatReadback` /
`ZagGpuCompatLaunch` contract. It bounds output slots, workgroup dimensions,
local work size, and waits before any Vulkan, OpenGL, or OpenCL call. The
OpenCL adapter also exposes an explicit `zag_opencl_compat_shutdown_process`
finalizer for ROCm worker-thread teardown; it uses Linux `exit_group` only when
the host deliberately chooses a process-level boundary, never implicitly.

MLIR is not part of this production contract. The existing `gpu-amd`,
`gpu-nvidia`, and `gpu-vulkan` textual MLIR targets are development/differential
frontends only. They do not submit work, do not prove physical execution, and
must never be silently selected for one of the production target names above.

Every production backend follows the same workflow:

1. Zag source is checked and lowered to the custom Zag GPU model.
2. A Zag-owned target encoder emits the target GPU's native ISA.
3. A strict Zag validator rejects unknown instructions, metadata, capabilities,
   and resource envelopes.
4. A pure-Zag userspace adapter calls the installed kernel driver's render-node
   UAPI directly for native targets. Compatibility targets use the explicit
   loader-backed boundary shown above; they do not rewrite or replace drivers.
5. Explicit ownership release, submission, exact fence retirement, and CPU
   acquire surround every physical operation.
6. Certification records device, driver discovery, firmware, kernel, compiler,
   and runtime hashes. Virtual evidence never promotes a physical tuple.

MLIR may be used inside the compiler as an interchange and optimization model,
but it is never a runtime API and cannot replace target ISA encoding, memory
management, command submission, synchronization, or presentation.

Adding a GPU family therefore means adding or extending a Zag code generator
and a thin direct kernel-UAPI adapter. It never means reimplementing a kernel
driver, but it does require per-family ISA and kernel-UAPI knowledge.
